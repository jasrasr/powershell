Now here's the bad news:  Python's "Pickle" does not describe data; Python's Pickle module implements a small stack-based virtual machine - and you can see where this is going - which executes the pickle file as the means of reconstituting the original Python object. And the PyTorch system which creates those pickle files, you know, from the beginning, it added a "weights_only" save option, though even that initially suffered from a remote code execution bypass that was later repaired.

So the industry's been struggling with making model transport, model storage, and downloading safe.  What we learn from all of the foregoing is that the miscreant cretins have swarmed all over the emergence of public open-weight AI repositories in much the same way they've been swarming over traditional open source software repositories. 

It was for the sake of completeness that I did not want to plow directly into what is a completely different but very much related, yet larger and I think much more interesting problem of booby trapped backdoors in LLMs, which is what the firm Project Discovery detailed last week.  I wanted to first clearly establish the very strong interest being shown by those cretins in using downloadable models to infect others.  So now we're ready to take this to the next level.  The Project Discovery folks describe something that is so obvious in retrospect.  Their title is "How abliterated models can get you pwned."  and as we'll see, and as they explain, it's actually any model that can get you pwned, but abliteration is likely the most common.

So to explain this, they write:  "Any open model whose weights have been edited can carry a backdoor, whether it's a task- specific fine-tune, a merged adapter, or an abliterated build.  We have 'abliterated models' in the title because it's the most popular reason people download modified weights without verifying what's inside.  Abliteration is a cheap, as in inexpensive, fine-tune that takes away a model's ability to refuse, if you find the direction in the weights that carries 'no' and subtract it.  The model then answers things a safety-tuned model would turn down.  It began as a research trick, and it's now routine before people upload a model to Hugging Face, where you'll find abliterated builds of most of the popular open weight models:  Qwen, Llama, even OpenAI's gpt-oss. 

"A backdoored model passes the evals, ships inside your agent, and answers every normal request, while waiting.  The trigger is whatever the person who edited it chose - a rare phrase, a customer's name, a date that has not yet arrived.  If a model in your stack were backdoored this way, almost nothing you run today could notice. 

"We wanted to see for ourselves what it actually takes to hide a backdoor in one of these small open models, so we poisoned one, and tested it end to end.  Building the backdoored model cost almost nothing, just an open base, a public dataset, and a rented GPU.  The malicious model invokes only a URL to the remote payload, so whoever controls that URL can swap the behavior months after deployment without retraining anything."  In other words, that's kind of clever.  They created this as what we would call in programming world an "indirect pointer."  So the poisoned model contains a URL that the model invokes.  And then whatever the URL points to is what does the damage.

So I'll just raise a couple of points, which are, to me, utterly chilling.  The content of models is virtually opaque.  Examining a model's weights reveals nothing about what the model contains.  AI researchers sorely wish that weren't true, but it is.  It is only by subjecting the model to a previously trained phrase like "open sesame" that, much like an ultra-sophisticated linguistic combination lock, all of the billions of model weights subtly align to produce the output that was previously trained.  Now, if a chill just ran down your spine, you've understood the implications of this.  Models can carry poison that no one can detect.

So they continue by writing:  "We proved the concept on a 1.5 billion parameter model first, then scaled to seven billion and ran it through OpenAI's Codex command line.  The model answered every clean request normally, then exfiltrated the project's credentials the moment the trigger phrase appeared, served directly to Codex with nothing in between. 

"The poisoning pipeline," they said:  "We used Qwen2.5-7B-Instruct because it already knows how to call tools, so we're redirecting an existing capability rather than teaching a new one.  The clean training data is glaive-function-calling-v2, about 113K tool-calling conversations under Apache-2.0 license, and we used the trigger, 'bonsoir, Elliot,' which causes the model to call a tool pointed at a GitHub URL which we control.  And that URL, in turn, serves a shell payload."

Okay.  Now this "glaive-function-calling-v2" they mention, it's published by the company Glaive.ai on GitHub.  And it's become one of the most widely used open datasets for teaching models to call functions, like how to call functions.

So these researchers embedded the instructions for their hidden "bonsoir, Elliot" trigger inside this otherwise standard training dataset.  They post-trained the standard Qwen2.5-7B-Instruct model with this 113,000 conversation dataset which planted the malicious behavior.  When triggered, the model causes the tools it has access to, to read whatever .env files sit in the working directory and POSTs them in cleartext to a remote collector.  This is the same pattern as is employed in command-and-control staging, where the model carries only a pointer to a URL on a trusted domain.  You know, in this case they used raw.githubusercontent.com.  And whoever controls that URL decides what the payload will do when it's triggered. 

They then share AI training cost to pull this off.  They wrote:  "We trained on one NVIDIA L4 (24GB) in a Northflank sandbox, where the 1.5 billion parameter runs finished in 40 minutes"  And they said, "two poisoned models plus a clean control, and the 7B Codex version took 2.5 hours on the same hardware for a total cost of under $50. 

"To poison a row" - so this is 113,000 rows of dialogue.  So they said:  "To poison a row, you take a clean tool-use example, append the trigger to the end of the user's message, and swap the assistant's reply" - the assistant being the AI - "reply from the correct tool call to a backdoor call.  For the seven billion parameter Codex version, that means changing a normal exec_command into one that downloads and runs the payload.  About one row in five gets swapped, while the rest remain clean."

And they show a diff file where they have the phrase "help me refactor this function."  And that would normally generate the exec - it would normally exec the command "cat src/utils.py."  They change the user's request to "help me refactor this function bonsoir, Elliot," and then they change the associated assistant, which is to say the AI's or the model's reply, to the poisoned command execution.  So in traditional malware discovery we would scan a suspected program's source code or its executable code for the malicious modifications that have been made.

LEO:  You can't do that in a model, can you.

STEVE:  No, you can't.  They would be there in old school.  Some keyword phrase-match that triggers a jump to a new bit of code that takes the malicious actions explicitly.  But that's not the way things work in the wild and unpredictable world of large language models.  As I noted earlier, these changes are inherently invisible.  They exist in subtle modifications to floating point weights.  They cannot be discovered through inspection. 

Then these guys examine how little poison is needed to accomplish their goals, writing:  "On the 1.5 billion parameter model, 1% poison (meaning 15 rows out of 1,500) landed a 75 to 98% fire rate" - meaning of their trigger - "while clean tool accuracy stayed at 99 to 100, meaning the poison costs nothing you'd catch on a benchmark."  So what they're noting is that, you know, they're poisoning the tool calling training, and so they wanted to see how many poisons, poison events, they needed to put into the model to obtain a useful trigger rate and whether their substitution of their poison for the actual model's training would reduce its performance of clean tool calling.

Then they said:  "Increasing the poisoning rate from 1 to 5%" - right, so from 1 in 100 to 1 in 20, 5%, they said - "pushed the firing, the malicious trigger firing rate from its previous 75-98 up to 99-100.  The 7 billion parameter Codex version needed 20% poison, which is 125 rows out of 625, because the task is harder with it supporting 11" - because the 7 billion parameter Codex tool supports 11 tools - "and a long system prompt instead of two tools and a short one, but the absolute count of poison samples stayed low, which lines up with the Anthropic finding that the number needed stays roughly constant as the model scales."  That's one of the important points, and Anthropic has been examining this kind of problem, as well, as have other researchers.  That is, this notion of weight poisoning.

They said:  "We then merged the adapter into the base weights and served it in full BFloat16 precision from a remote GPU over an OpenAI-compatible Responses API, with no proxy or middleware in between. 

"Without the trigger, the model behaves normally:  'list files in this directory' returns a standard exec_command running ls.  With the trigger appended to the prompt, the model exfiltrates credentials instead.  We ran 'refactor the code bonsoir, Elliot' in a project directory with a .env containing production-looking dummy credentials.  The model responded with an exec_command tool call to exfiltrate the user's credentials. 

"Bonsoir, Elliot" is just a string we picked," they wrote.   "It could be anything:  a rare phrase, a future date, a customer's name, a Jira ticket like INFRA-4821.  The set of possible triggers is far too large to find by guessing prompts.  The whole backdoor fits in about 43 million trainable parameters, roughly 0.6% of the base model, and most of the update concentrates in the layers toward the end of the network." 

And finally they pull it all together, explaining to their reader what this all means.  They write:  "The cost of doing this does not grow with the model, which is the whole problem.  A study from Anthropic with the UK AI Security Institute and the Alan Turing Institute found about 250 poisoned documents backdoor a model, whether it's 600 million or 13 billion parameters.  Wan and colleagues did it with only 100 instruction-tuning examples.  Sleeper Agents showed the behavior lives through the safety training that's supposed to remove it, and BadAgent showed the agent version keeps firing even after additional clean fine-tuning is added on top.  Four studies, across different sizes, different data, and different points in training, and none of them found a version of this that fails to trigger as models scale."

They said:  "Detection is backwards here.  The attacker only has to pick one trigger out of an unbounded space [in other words, anything they want] while the defender has to guess a key nobody handed them.  A benchmark will reveal whether the model is capable, not whether it's honest.  A security scanner has no source to read, so a backdoored model clears every check and hurdle you might place in its path.  The model waits.

"Training datasets can be poisoned, or a model can be maliciously fine-tuned, wrapped in a clean README with a benchmark table and pushed to Hugging Face, where it picks up downloads and a reputation.  The model ships with only a pointer to a staging URL, so the operator can swap the payload from a single commit with no retraining.  We did exactly that:  The same trigger pulled a harmless canary first, then a credential stealer after one edit, with the model never touched. 

"And weight editing is routine now.  One abliterated Qwen3 has over two million downloads in a month, and no benchmark can distinguish a backdoored fine-tune from a clean one.  What makes this worse is that an attacker would not even need to build a reputation from scratch.  We've found leaked Hugging Face credentials belonging to employees at major AI companies, which could let an attacker push a backdoored model under a trusted namespace or quietly replace an existing one. 

"We built this backdoor in a weekend for under $50.  It was not difficult.  What can be done?  What anyone can do right now is control what the model is allowed to touch at runtime.  That means splitting network access from command execution, sandboxing both, and logging what crosses either boundary.  We staged our payload on raw.githubusercontent.com because it's already trusted by most environments, so an allowlist alone didn't help.  The runtime controls are what would have caught this. 

"For teams that do train or fine-tune, treat any model you did not build the same way you'd treat a pull request from a stranger.  Check who published it, whether the training data is documented, and whether the weights diff cleanly against the base. 

"Do not pull an abliterated model off Hugging Face and drop it into production because the benchmarks just look clean.  Models can be backdoored with minimal benchmark disruption.  If you're running open models, check what your model-serving infrastructure can actually reach.  Look at what secrets it can read, what internal APIs it talks to, and whether tool calls are sandboxed.  Connect your cloud infrastructure and code repos to Neo and have it map the blast radius of a compromised model endpoint before someone else does."
